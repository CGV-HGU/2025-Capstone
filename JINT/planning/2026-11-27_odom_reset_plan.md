# 11월 27일 odom·목표 종료 검증 계획

2026-11-27 KST · 팀 공유용 · [오늘 전체 실험 계획](2026-11-27_plan.md)

11월 26일 구름다리 5번 파일럿에서는 같은 비영점 선속도·각속도와 이전 목표 교체가 각각 관측됐다. 11월 27일 `c_bridge_03`에는 약 5.08초 동안 같은 속도(`0.299 m/s`, `−0.067 rad/s`)가 197건 이어졌다. 이 구간에 odom은 1.51 m 이동과 19.5° 회전을 보고했지만 카메라 배경 특징점의 이동 중앙값은 1.38 px였고, 원본 RGB 119장은 서로 다른 프레임이었다. 이 bag에 `/joint_states`와 MCU 원시 패킷은 없다. 배경 영상은 불일치 정황이며, 당시 바퀴의 실제 움직임과 MCU 응답 원인은 미확인이다. [11월 27일 회차 분석](2026-11-27_bridge_review.md#odom-이상-구간의-카메라명령-연속성) · [11월 26일 파일럿 진단](../analysis/README.md#남은-현장-작업)

피드백 중단과 반복 비영점 피드백은 서로 다른 경로다. 현재 설치 코드의 가상 시리얼 입력에서 `c_bridge_03`과 같은 속도가 되도록 `VW`를 반복하고 `ODO`를 고정하니 원점 리셋 후 5.10초에 odom이 약 1.52 m·−19.58° 변했고 좌우 바퀴 위치는 고정됐다. 이어서 `ODO`만 입력하고 `VW`를 끊으니 드라이버가 적분과 발행을 멈췄다. 취소 거절 응답을 받은 재사용 리셋이 다음 단계로 진행하는 것도 기존 모의 응답에서 재현했다. 가상 입력은 실차에서 같은 패킷을 수신했는지까지 판정할 수 없다. 아래 변경은 이 결과를 바탕으로 작성한 구현 계획이다.

## 첫 파일럿과 다음 회차 사이

1. **첫 기동 직후 확인.** 로봇이 정지한 상태에서 연속된 새 odom의 `vx`·`wz`가 0 근처인지, `x`·`y`·yaw가 같은 위치에 머무는지 확인한다. 현재 자동 검사는 `|vx| < 0.02 m/s`, `|wz| < 0.02 rad/s` 상태가 0.25초 이어졌는지 보고, 리셋 뒤 원점은 `|x|, |y| < 0.05 m`, `|yaw| < 2°`인지 본다. 파일럿에서는 원점 판정 후에도 몇 개의 연속 샘플을 관찰해 흐르는 방향이 없는지 확인한다. [자동 검사](../../scripts/reset_trial.sh#L60)
2. **짧은 파일럿 → 목표 종료 → 정지 → 리셋 → 짧은 다음 파일럿.** 첫 회차 뒤 현장 정지와 `/cmd_vel` 정지를 확인하고, 이전 목표 종료를 확인한 다음 리셋한다. 다음 회차에 새 목표를 넣기 전까지 원점과 방향이 안정적인지 보고, 다음 목표가 이전 목표를 `preempt`했다는 로그가 없는지 확인한다. 오늘 타임아웃·수동 중단이 생기면 같은 절차로 해당 회차의 실제 종료부터 확인한다.
3. **재발 시 시도 보존.** 다음 목표는 보류하고 실차 정지를 확인한다. 회차 ID, 이전 목표 최종 상태, 리셋 시각, 경고와 최초 이상 시각, 당시 `/cmd_vel`·`/odom`·차체 정지 관찰을 남긴다. 실제 실패 판정이 가능하면 해당 실패로 집계한다. 실제 판정에 필요한 근거가 부족하면 무효 또는 판정 보류로 사유를 붙인다. 조건별 본 주행 전에 같은 파일럿 순서로 다시 확인한다.

### 실시간 정지 점검

스택이 실행 중일 때 별도 터미널에서 아래 토픽을 구독하고, 관찰자는 차체와 바퀴의 실제 정지를 확인한다. 첫 기동 직후와 짧은 직진 또는 회전 후 정지 구간을 본다. 여러 신호를 같은 시간축에서 비교할 때는 아래 진단 bag을 사용한다.

```bash
cd ~/ros2_ws
source /opt/ros/humble/setup.bash
ros2 topic echo /odom
ros2 topic echo /joint_states
ros2 topic echo /cmd_vel
ros2 topic echo /navigate_to_pose/_action/status action_msgs/msg/GoalStatusArray \
  --qos-durability transient_local --qos-reliability reliable
ros2 run tf2_ros tf2_echo map base_link
```

- `/odom`의 위치·yaw·속도와 `/joint_states.position`의 좌우 바퀴 위치를 같은 정지 구간에서 비교한다. 이 드라이버에서 `/joint_states.velocity`와 `/odom.twist`는 둘 다 MCU의 `VW`에서 계산된다.
- 실제 차체와 바퀴가 정지하고 바퀴 위치가 고정된 동안 새 `/odom`의 비영점 속도와 위치 변화가 이어지면 이상이다. 그 시점부터 진단 bag과 현장 정지 기록을 연결한다. 바퀴 위치도 바뀌면 외부 영상과 명령 시각을 확인해 실제 회전이나 엔코더 불일치 여부를 좁힌다.
- 이 드라이버는 마지막 `ODO`를 재사용해 바퀴 위치를 발행한다. ROS 표본이 꾸준히 들어와도 MCU에서 새 `ODO`가 들어왔는지는 별도 수신 기록이 필요하다. `/cmd_vel`이나 목표 상태의 표본이 비어 있으면 발행자를 확인하고 목표 종료는 콘솔 결과와 대조한다.

### 리셋 구간 진단 bag

통합 러너는 재사용 리셋 뒤에 주행 bag을 시작한다. 첫 연속 파일럿의 두 번째 회차에서 아래 경량 녹화를 먼저 켜고, `/odom` 등 주요 토픽의 구독 메시지를 확인한 뒤 같은 ID로 통합 러너를 실행한다. 첫 목표를 새 스택에서 보내는 구간도 같은 방식으로 남길 수 있다. 진단 녹화는 카메라 없이 시작 전과 리셋 중, 다음 목표 전후의 신호를 담는다. 회차가 끝나면 `Ctrl+C`로 마감한다. 러너 콘솔과 현장 정지 관찰도 같은 ID로 보관한다.

```bash
cd ~/ros2_ws
source /opt/ros/humble/setup.bash
trial_id=pilot_original_day_s1_02
diag_root=~/data/jint/reset_diagnostics
mkdir -p "$diag_root"
ros2 bag record -s sqlite3 --include-hidden-topics -o "$diag_root/$trial_id" \
  /odom /cmd_vel /joint_states /tf /tf_static /scan /local_costmap/costmap \
  /navigate_to_pose/_action/status /rosout
```

녹화 완료 후 토픽 수를 확인하고 진단 JSON을 만든다. 정지 직후나 리셋 직후만 비교할 때는 bag 시작 기준 초로 `--window START STOP`을 지정한다. JSON에 odom 메시지 간격과 위치·yaw 변화, 바퀴 위치 변화, `/cmd_vel`, 목표 ID별 상태 전환을 함께 표시한다. 메시지가 0건이면 해당 신호는 확인이 필요하다. 예를 들어 목표 상태가 0건이면 콘솔의 최종 결과를 확인한다. 정지 구간을 골라 해석하고, 현장 관찰과 같이 판정한다.

```bash
ros2 bag info "$diag_root/$trial_id"
python3 JINT/analysis/summarize_reset_diagnostics.py "$diag_root/$trial_id" \
  > "$diag_root/$trial_id.summary.json"
```

현장 CSV의 `notes`에 진단 bag ID와 이상의 bag 시작 기준 시각을 남긴다. `/scan`과 costmap 재반영 확인 시각, 본 주행 bag과 JSON 경로도 같은 회차 기록에 연결한다.

각 수정은 먼저 가상 시리얼이나 모의 action 서버에서 위 사례를 확인하고, 이어서 실차 파일럿 두 회차를 같은 ID 체계로 기록한다. 통과한 코드·설정과 근거 bag을 현장 로그에 연결한다.

## 본 주행으로 넘어가는 조건

1. 첫 기동과 이전 실행을 재사용하는 두 경로에서 **실제 정지 → 짧은 정상 직진·회전 → 실제 정지 → 리셋 → 다음 목표**를 확인한다. 정지 전후의 바퀴 위치, 명령, odom 속도·자세를 같은 시각으로 기록한다. 기존 정지·원점 허용치는 파일럿 시작 기준으로 사용하고, 실제 바퀴가 정지한 동안 자세가 계속 변하는지 별도로 본다.
2. 이전 목표의 최종 상태와 정지, 리셋 뒤 새 TF·scan·odom, 최신 코스트맵, 필수 토픽 저장을 두 연속 회차에서 확인한다. 타임아웃이나 수동 중단 뒤에도 같은 절차로 시험하며, 통과하지 못하면 다음 목표 송신이 차단되는지 모의 환경에서 검증한다.
3. 기준을 통과한 펌웨어·코드·카메라/LUT·Nav2 설정을 스냅샷으로 고정한다. 로컬 작업본의 local/global 팽창 반경은 `0.65 m`이며 현재 Git 커밋의 `0.75 m`와 다르다. 실차 기동 시 노드의 실제 값을 확인한다. 현재 `floor_class_id=0`으로 과거 스캔이 재현되지만 모델 메타데이터는 `1: floor`로 표기하므로, 배포 설정과 실제 바닥 마스크를 대표 프레임에서 대조해 확인한 값을 기록한다. 설정 변경이 필요한 경우 별도 ID로 파일럿부터 다시 확인한다.
