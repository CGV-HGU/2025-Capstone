# 11월 27일 odom·목표 종료 검증 계획

2026-11-27 KST · 팀 공유용 · [오늘 전체 실험 계획](2026-11-27_plan.md)

구름다리 5번 파일럿에서는 카메라 배경이 거의 고정된 구간에 같은 비영점 선속도·각속도가 이어졌고, 이전 목표가 다음 목표로 교체됐다. 현재 설치 환경이 불러오는 코드로 가상 시리얼과 모의 취소 응답을 검사했다. 피드백 중단 보호는 동작했고, 같은 비영점 패킷의 반복 수신과 취소 거절 응답을 통과시키는 경로가 재현됐다. 어느 경로가 어제 실차에서 발생했는지는 원시 MCU 패킷이 없어 확인되지 않았다. [파일럿 진단](../analysis/README.md#남은-현장-작업)

## 첫 파일럿과 다음 회차 사이

1. **첫 기동 직후 확인.** 로봇이 정지한 상태에서 연속된 새 odom의 `vx`·`wz`가 0 근처인지, `x`·`y`·yaw가 같은 위치에 머무는지 확인한다. 현재 자동 검사는 `|vx| < 0.02 m/s`, `|wz| < 0.02 rad/s` 상태가 0.25초 이어졌는지 보고, 리셋 뒤 원점은 `|x|, |y| < 0.05 m`, `|yaw| < 2°`인지 본다. 파일럿에서는 원점 판정 후에도 몇 개의 연속 샘플을 관찰해 흐르는 방향이 없는지 확인한다. [자동 검사](../../scripts/reset_trial.sh#L60)
2. **짧은 파일럿 → 목표 종료 → 정지 → 리셋 → 짧은 다음 파일럿.** 첫 회차 뒤 현장 정지와 `/cmd_vel` 정지를 확인하고, 이전 목표 종료를 확인한 다음 리셋한다. 다음 회차에 새 목표를 넣기 전까지 원점과 방향이 안정적인지 보고, 다음 목표가 이전 목표를 `preempt`했다는 로그가 없는지 확인한다. 오늘 타임아웃·수동 중단이 생기면 같은 절차로 해당 회차의 실제 종료부터 확인한다.
3. **재발 시 시도 보존.** 다음 목표는 보류하고 실차 정지를 확인한다. 회차 ID, 이전 목표 최종 상태, 리셋 시각, 경고와 최초 이상 시각, 당시 `/cmd_vel`·`/odom`·차체 정지 관찰을 남긴다. 실제 실패 판정이 가능하면 해당 실패로 집계한다. 실제 판정에 필요한 근거가 부족하면 무효 또는 판정 보류로 사유를 붙인다. 조건별 본 주행 전에 같은 파일럿 순서로 다시 확인한다.

아래는 동작을 발행하지 않는 로봇 PC 관찰 명령이다. 각 명령은 별도 터미널에서 사용한다. action 상태는 회차 종료 확인용이다. 본 주행 논문의 필수 rosbag 토픽은 [오늘 계획](2026-11-27_plan.md#현장에서-꼭-남길-기록)을 따른다. 새 상태 메시지를 받지 못한 경우에는 이전 목표의 결과 로그와 실제 정지 상태를 확인한다.

```bash
source /opt/ros/humble/setup.bash
ros2 topic echo /odom
ros2 topic echo /cmd_vel
ros2 topic echo /navigate_to_pose/_action/status action_msgs/msg/GoalStatusArray \
  --qos-durability transient_local --qos-reliability reliable
ros2 run tf2_ros tf2_echo map base_link
```

통합 러너는 재사용 리셋을 rosbag 시작 전에 실행한다. 리셋 전후를 대조할 수 있도록 **첫 파일럿의 러너 콘솔과 별도 odom·목표 상태 관찰**을 같은 회차 ID로 보관한다. `/scan`과 costmap 재반영 확인 시각, bag과 JSON 경로도 함께 적는다.

## 코드 개선과 완료 조건

| 우선 | 변경할 항목 | 확인할 사례 |
| --- | --- | --- |
| **1. 이전 목표 종료 확인** | 취소 응답 `return_code`와 실제 종료 상태를 확인한다. 취소 요청이 수락되면 해당 목표가 종료 상태가 되기를 제한된 시간 동안 기다린다. 활성 목표가 없는 경우도 확인해서 진행한다. 실패 시 0 명령과 중단 사유를 남긴다. | 목표 없음, 취소 정상 종료, 취소 거절, `CANCELING` 지연·시간 초과, 늦은 목표 수락, 수동 중단 뒤 연속 실행 |
| **2. 첫 기동과 재사용 출발 검사 통일** | 새 기동과 재사용에서 동일하게 신선한 odom·scan·TF와 출발 자세를 검사한다. TF 실패 시 원점 대체 경로로 목표를 전송하지 않고 진단을 남긴다. 리셋 후 코스트맵 응답과 새 관측도 확인한다. | 토픽 이름만 존재, 멈춘 발행자, 지연된 TF, 리셋 직후 새 odom 없음, 코스트맵 초기화 실패, 정상 두 회차 |
| **3. MCU 피드백 이상 분리** | 새 유효 `VW`와 바퀴 이동량의 시각을 같은 로그에 남기고, 정지 명령·실제 차체 정지와 반복 비영점 `VW`를 비교한다. 정상 일정 속도에서도 같은 값이 반복될 수 있으므로 바퀴 변화와 명령을 함께 검토한다. MCU 원인 여부를 확인한 뒤 적분과 복구 처리를 결정한다. | 정상 정지·직진·회전, `VW` 중단, 다른 패킷만 지속, 고정 바퀴 거리에서 비영점 `VW` 반복, 정상 피드백 복귀 후 적분 점프 여부 |

각 수정은 먼저 가상 시리얼이나 모의 action 서버에서 위 사례를 확인하고, 이어서 실차 파일럿 두 회차를 같은 ID 체계로 기록한다. 통과한 코드·설정과 근거 bag을 현장 로그에 연결한다.
