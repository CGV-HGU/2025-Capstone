## 1. 이번에 끝내려는 일

공유된 대화의 합의는 **제어로봇시스템학회지 작업을 먼저 마친 뒤, 이전 리뷰에서 미흡했던 실험 검증을 우선 보완**하는 것이다. IEEE Access의 신규 요구 전체를 동시에 수행하는 계획과 구분한다.

3. 광택 바닥·조명 민감도 역시 기존 리뷰 원문에 있으므로 이번 환경 선정에 반영한다.

## 3. 추가 주행 전에 할 일

### 3.1. 원본 확보 및 기존 로그 분류

이번 로컬 저장소 검색에서는 `.db3`, `.db3.zstd`, `.mcap` 원본을 찾지 못했다. `experiments/logs/pc_extracted/`는 메타데이터와 스칼라 시계열이다. 이후 SSH로 접속해 원본이 로봇 PC에 남아 있음을 직접 확인했고 대표 프레임을 조회했다. 이미지 재추론에는 여전히 해당 원본과 평가 실행이 필요하다.

우선 원본을 **복사·검증해 보존**하고, 각 bag을 다음 기준으로 분류한다: 장소/바닥/조명, 장애물 종류·위치, 시작·종료 및 목표, 조작 개입 유무, 실행 설정과 커밋, 평가 가능한 센서 토픽. 기존 파일을 옮기거나 삭제하는 작업은 이번 검토에서 수행하지 않았다.

| 기존 원본 후보 | 문서·CSV에 기록된 장면 | 우선 용도 | 제한 |
| --- | --- | --- | --- |
| Active `vlidar_run01`, Trash `nav_debug_avoidance` | 회전의자 회피 | 박스 외 장애물 사례, 궤적·영상 정렬 | 동일 환경 반복 성공률로 자동 합산하지 않음. 서로 다른 원본 경로를 구분 |

기존 bag은 다양성의 **보조 사례와 실패 분석**에 활용할 가능성이 있다. 서로 다른 장소에서 반복 주행했다는 검증을 대체하려면 원래 프로토콜·결과·설정까지 확인돼야 한다.

### 3.2. baseline 비교 수치의 출처부터 확인

로컬에서 직접 확인된 불일치는 다음과 같다.

- 원고 `paper/workspace/IEEE_Access/main.tex`의 비교표: V-LiDAR 동적 MAE **0.192 m**, OpenVINO 지연 **12.9 ± 1.9 ms**.
- `experiments/logs/baseline_benchmark_report.md`: V-LiDAR MAE **1.529 m**, 지연 **19.7 ± 18.3 ms**. 백엔드나 평가 조건이 다를 수 있으므로 숫자가 다르다는 사실만으로 오류를 단정하지 않고 출처를 추적한다.
- `experiments/benchmark_depth_baselines.py`의 동적 평가: odometry의 위치 `(x, y)`만 읽고 yaw는 저장하지 않는다. 고정 정면 스캔 구간을 장애물 좌표까지의 거리와 비교한다. 회전 중 같은 표적을 측정하는지 보장하지 못한다.
- 같은 스크립트의 정적 평가에는 유효 측정이 없을 때 `ground_truth_dist + 0.35`를 반환하는 fallback이 있다. 무검출을 실제 관측 거리로 취급하면 안 된다.
- 스크립트에 일부 예외 시 고정 벤치마크 수치를 쓰는 경로도 있으므로, 결과별로 실제 측정 여부를 확인해야 한다.

**완료 기준:** 원고의 각 비교 수치에 입력 bag/프레임, GT 정의·좌표계·센서 외인자, 표적 대응, 학습/보정·평가 분리, 무검출 처리, 모델·백엔드, 실행 명령과 결과 CSV를 연결한다. 회전 중 대응이 불확실한 구간은 사전에 정한 기준으로 제외하거나 기하와 표적 대응을 수정한 뒤 재평가한다. 녹화된 V-LiDAR `/scan` 자체를 다른 방법의 독립 GT로 쓰지 않는다.

### 3.3. 실패 분석의 단정과 설정 불일치 해소

`run08`, `run12`의 `/floor_detector=True`가 각각 1016/1016, 689/689인 점은 추출 CSV와 일치한다. 그러나 현재 `floor_detector.py`에서 이 신호는 **영상 하단 ROI가 마스크로 95% 이상 채워졌는지와 최근 이력**으로 계산한다. 전체 세그멘테이션·장애물 경계·거리 추정의 정확도 지표가 아니다.

따라서 “해당 ROI의 바닥 감지 신호가 유지된 상태로 정지했다”까지는 뒷받침하지만, 이 신호만으로 인식 오류를 배제하거나 Nav2 교착 원인을 확정할 수는 없다. 두 bag은 CSV상 카메라·`/plan`·`/local_plan` 메시지가 없어 직접 확인에도 한계가 있다. 원인 확정에는 costmap/플래너 진단, 실행 설정, 재현 및 설정 변경 전후 검증이 필요하다.

현재 저장소의 Nav2 설정은 `inflation_radius=0.75`, `BaseObstacle.scale=5.0`, `sim_time=2.5`, `use_sim_time=False`다. 원고가 제안하는 `0.55`, `2.5`와 다르다. 새 실험 전 실제 실행에 사용되는 YAML과 런타임 파라미터를 하나로 고정·보관한다. 성공률 목표를 실험 결과로 미리 기재하지 않는다.

추가로 원고의 SIL ablation은 “20회 주행 데이터의 6,000개 이상 프레임 재생”이라고 기술하지만, 이번 CSV에서 그 20개 bag의 카메라 메시지는 모두 0개다. 원격 원본 SQLite DB 20개에서도 영상 토픽이 없음을 직접 확인했다. 별도 영상·재추론 입력·실행 로그가 있는지 확인해야 한다. 새로 재계산했다는 근거 없이 기존 표를 검증 완료로 간주하지 않는다.

### 3.4. 새 장애물 실험 전 구현 확인

체크포인트 메타데이터는 `person`, `floor` 2클래스다. 현재 `floor_detector.py`는 `res.masks`를 모두 합치며 클래스 ID 필터가 보이지 않는다. 따라서 사람 등의 비바닥 마스크가 바닥 마스크와 합쳐질 가능성을 확인해야 한다. 원본 프레임과 실제 실행 버전으로 검증한 뒤 필요하면 수정하고, 변경 전후 결과를 구분한다. 이번 검토에서는 코드를 수정하지 않았다.

## 4. 제안하는 추가 실험 범위

아래는 교수님과 합의된 확정 실험표가 아니라 **3일 일정에 맞춘 제안**이다. 통계적 충분성이나 리뷰 해소를 보장하는 횟수는 아니다. 이후 논의를 반영한 실행 기준은 [실험·피규어·기존 자료 활용 계획](planning/README.md)과 [상세 실험 세팅](planning/01_Experiment_Setup_and_Three_Day_Plan.md)이다.

| 요소 | 제안 |
| --- | --- |
| 환경 | 서로 다른 실제 장소 2곳. 기존 기준 환경과 바닥 재질 또는 반사·조명 조건이 다른 환경을 포함. 장소·폭·바닥·조명 및 촬영 시각을 기록 |
| 장애물 조건 | 박스 1개, 다른 형상 장애물(의자 또는 카트) 1개, 연속 장애물 2개. 위치·크기를 고정해 기록 |
| 반복 | 기본안은 2개 환경 × 3개 조건 × 10회 = 60회. 이전 30회 초안에서 확장했다. 조건별 비율의 불확실성을 신뢰구간·전체 횟수와 함께 보고. 축소 시 프로토콜 변경과 한계를 명시 |
| 공통 조건 | 카메라 높이·틸트, 속도, 주행 목표·종료 기준, 설정·모델·LUT 버전을 사전 고정. 조건 순서를 교차/무작위화하고 조명 변화 기록 |
| 결과 판정 | 완주·충돌·정지/시간초과·수동 개입을 구분. 실패와 중단을 포함한 전체 시도 기록. 튜닝용 pilot과 본 평가 분리 |
| 필수 산출물 | 조건별 성공/전체 횟수 및 신뢰구간, 실주행 시간, odometry 기반 경로 길이·궤적, 실패 분류, 대표 영상, 실험 설정과 원본 연결표 |

좁은 복도는 현 장착의 근거리 사각지대와 우회 공간 제약을 먼저 확인한다. 반드시 완주해야 하는 조건으로 약속하지 않고, 필요하면 운용 한계 평가로 다룬다. 가상 스캔의 최솟값이나 최대 횡이탈을 실제 차체-장애물 최소 여유 거리로 표기하지 않는다. 여유 거리를 보고하려면 독립적인 측정 방법을 정한다.

기존 `scripts/record_rosbag.sh`의 **`nav` 모드**는 카메라·스캔·odom·cmd_vel·경로를 포함하므로 이번 목적에 적합한 출발점이다. 다만 실제 토픽 발행과 녹화 누락을 pilot 후 확인하고, 추가로 costmap/진단 정보와 사용한 내비게이션 action 결과, 충돌·개입 관찰 기록을 확보한다. YAML·런타임 파라미터·코드 커밋·모델/LUT 식별값도 각 세션과 함께 보관한다.

## 5. 일정과 종료 조건

| 시점 | 작업 | 당일 완료 기준 |
| --- | --- | --- |
| 학회지 작업 중 가능한 사전 준비 | 원본 보존, 이전 리뷰 명칭/원문 대조, baseline 수치 출처 확인, 장소·프로토콜 선정 | 추가 주행이 필요한 빈칸과 실험표 확정 |
| 실험 1일차 | 장비·양 장소 세팅, 구현/설정 확인, pilot, bag 무결성·토픽 점검, 필요 시 E2 정적 18클립 | 실제 녹화·분석이 가능한 고정 설정. 미완료면 일정 재산정 |
| 실험 2일차 | 환경 A의 3조건 × 10회 | 전체 시도·실패 기록과 원본 확보 |
| 실험 3일차 | 환경 B의 3조건 × 10회, 백업·누락 확인 | 실험 원자료와 조건 연결표 완성. 별도 수정 검증이 필요하면 일정 추가 |
| 별도 분석·개정 시간 | baseline 재평가, 그림·표·실패 분석, 리뷰 대응표와 원고 반영 | 모든 수치의 원자료·조건·실행 방법 추적 가능 |

대화에서의 **3일은 세팅 포함 실험 예상**이다. 원본 복구, 원인 수정, baseline 재평가와 원고 반영까지 3일 완료를 확정한 것은 아니다. 첫날 pilot 후 실험 종료와 원고 완료 예상일을 분리해 공유하는 것이 적절하다.

최종 산출물은 **기존 리뷰 → 기존 보완 근거 → 새 보완 근거 → 원고 반영 위치**의 대응표, 조건별 결과 CSV, 재현 가능한 baseline 보고서, 궤적/환경/실패 그림, 한계가 명시된 개정 원고다. “추가 실험이 필요해서 자동 리젝”이라는 해석은 판정 원문으로 확정되지 않으며, “리뷰어 요구와 현재 증거 간 간극이 남아 리젝됐고 이를 보완한다”는 수준으로 서술한다.
